# Reverse-engineered DJI protocols (DUML / DJI CAN / Open Protocol) as a passive source of waypoint-mission status on the M600 (A3 / A3 Pro + Lightbridge 2)

Research date: 2026-10-14. Primary sources opened: o-gs/dji-firmware-tools (shallow clone of master, last commit 2026-07-21, `195692263c`), its GitHub issues and wiki index, DJI Onboard-SDK repo (branch 3.9, last commit 2019-09-24), the DJI OSDK "Ground Station Protocol" doc page, the DJI A3/A3 Pro User Manual (2016.05 V1.0, text extracted from the PDF), the STorM32 wiki DJI CAN page, and the JKU thesis "DJI Wi-Fi Protocol Reverse Engineering" (Christof, Nov 2021).

**Overall verdict:**
- **Sniffing DUML/CAN on the M600's internal buses: does not work.** Nothing public lets a passive tap read mission status there. The DUML command IDs for mission status exist and are named, but their payload layouts are marked "unverified" by the dissector authors. No public source shows that this traffic, or any decode of it, appears on a bus that can be tapped on the A3, the A3 CAN, or the Lightbridge 2 to A3 "RF port" link.
- **Listening on the API UART the ESP32 already reads: likely works, with caveats (to be checked on the bench).** Besides the 0x02/0x00 broadcast, DJI's Open Protocol defines two separate unsolicited pushes on the same API UART: **CMD set 0x02 / CMD ID 0x03, "Current Mission Status Push"** (mission_type, target_waypoint, current_status, error_notification) and **0x02 / 0x04, "Mission Event Push"** (upload finished, mission finished, waypoint reached with waypoint_index). DJI calls them "broadcast data protocol", not API calls. The documented prerequisite is the "Ground Station Status" checkbox in DJI Assistant. That is a configuration step, not a transmission by the payload. No source says whether these pushes fire for missions started from GS Pro or DJI Pilot rather than from the OSDK. This is the key empirical unknown.

## 1. What o-gs/dji-firmware-tools documents about DUML waypoint/mission commands, and which platforms it covers

### Takeaway
DUML command set 0x03 (Flight Controller) has a full block of named mission commands, from 0x80 to 0x9E. Two of them are unsolicited pushes from the flight controller: **0x88 "Push Navigation Status Info"**, which carries Target Way Point and running status, and **0x89 "Push Navigation Event Info"**, which carries Reach/Finish/Upload incidents and the reached waypoint index. These are the only mission commands with payload dissectors, and the waypoint fields are commented "unverified". The dissectors come from UART, USB and Wi-Fi captures and from DAT logs of consumer drones (Phantom 3/4, Mavic, Spark). The A3 and N3 appear only as enum values (flight-controller type 0x0a = 'A3', 0x14 = 'N3'). Nothing shows A3, M600 or LB2 captures.

### Inferences
- The DUML 0x03/0x88 field set (mission type, target waypoint, running status, error notification) matches the OSDK Open Protocol 0x02/0x03 mission-status push in Section 2 almost field for field. Likely the FC builds one internal "navigation status" record and exports it both as a DUML push toward the app/RC and as an Open Protocol push on the API UART. This is an inference from the field layouts, not a documented fact.
- Since the A3 is in the FC-type enum, A3-era firmware probably speaks the same DUML v1 family. But I found no public capture of an A3 or M600 to confirm the mission payload layouts on that firmware.

### Gaps
- No public payload layout for 0x82/0x84 (mission and waypoint upload), so a full waypoint list could not be decoded even if captured.
- The A3, N3 and M600 wiki/board pages could not be confirmed absent from the full 161-page wiki. Only 15 titles are visible on the index, and my `git clone` of the wiki stalled.

## 2. Which physical links on the M600 carry this traffic, and has anyone sniffed them? Is mission upload or progress visible on a tappable bus?

### Takeaway
On the A3, the Lightbridge 2 air system connects through the **"RF Port" with a "DBUS Cable II"**, not through CAN1. CAN1 is the "Dedicated DJI CAN-Bus port" for the GPS-Compass Pro, RTK and other DJI devices, CAN2 and the API port are for SDK devices, and the LED, PMU, IMU and iESC ports are separate. So the mission path RC → LB2 air → A3 most likely does **not** cross CAN1 at all. It probably goes over the proprietary RF-port link, whose electrical protocol is undocumented (unverified forum guesses only). Nobody has published A3 CAN or A3 RF-port sniffing. The only public DJI-CAN decoding is for the older Naza-M V2, and that data had to be *requested* by transmitting a heartbeat. The only passively readable, documented mission source is the Open Protocol 0x02/0x03 and 0x02/0x04 push on the API UART.

### Inferences
- On the M600, the mission most likely reaches the A3 over the LB2 air unit → A3 "RF port" link (DBUS Cable II), possibly with some traffic over CAN as well. Neither path has a public decode. Tapping the RF port would mean inserting into the cable that carries the RC link to the flight controller. That is the highest-risk wire on the aircraft and is not recommended.
- Even if mission DUML traffic does cross CAN1, no public work describes how DUML maps onto CAN frames on the A3 (IDs, fragmentation). Prior Naza work shows DJI CAN data can be gated behind a heartbeat the listener must transmit, which is forbidden in this project.
- The lowest-effort and lowest-risk test fits the existing setup. With "Ground Station Status" (SDK page, DJI Assistant 2) enabled, log every Open Protocol frame on the API UART during a GS Pro mission and look for `cmd_set=0x02, cmd_id=0x03/0x04`. If they appear, waypoint index, reached events and mission finish are available receive-only, with no new hardware. If they do not appear, the pushes are probably gated on OSDK-owned missions or on activation.

### Gaps
- No source says whether 0x02/0x03 and 0x02/0x04 are emitted when the mission comes from GS Pro or DJI Pilot (MSDK) rather than from the OSDK, or whether they require the OSDK app to be activated.
- No source names the electrical protocol on the A3 "RF port" (UART baud, S.Bus/DBUS plus serial).
- No source confirms whether the LB2 air unit connects to CAN1.
- No public A3, N3 or M600 CAN capture or ID map was found (searched GitHub issues, the web, the DJI SDK forum and the STorM32 wiki).

## 3. Encryption or authentication on A3-era DUML, CAN and the Lightbridge 2 link

### Takeaway
The DUML v1 header has a 3-bit encryption-type field (None / AES-128 / Self Def / XOR / DES / AES-192 / AES-256). Public analyses of consumer drones found the application payload unencrypted in practice. That evidence covers the Mavic Pro 1 over Wi-Fi only. Nothing public addresses encryption on the A3 CAN bus or the LB2 air-to-A3 link. The Open Protocol (API UART) has its own optional encryption flag. The project's ESP32 already decodes the 0x02/0x00 broadcast, so that link is evidently readable in the current configuration.

### Cited Findings
- `DJI_DUMLv1_ENCRYPT_TYPE_TEXT = { [0] = 'None', [1] = 'AES 128', [2] = 'Self Def', [3] = 'Xor', [4] = 'DES 56', [5] = 'DES 112', [6] = 'AES 192', [7] = 'AES 256' }` — [dji-dumlv1-proto.lua](https://github.com/o-gs/dji-firmware-tools/blob/master/comm_dissector/wireshark/dji-dumlv1-proto.lua)
- `comm_mkdupc.py` defines `ENCRYPT_TYPE` (`AES_128 = 1` … `AES_256 = 7`) and General-set encryption commands (`DJIPayload_General_EncryptCmd`, `DoEncrypt = 4`, `EncryptConfigRq`). `comm_serialtalk.py` defaults to `--encrypt_type default="NO_ENC"` — [comm_mkdupc.py](https://github.com/o-gs/dji-firmware-tools/blob/master/comm_mkdupc.py); [comm_serialtalk.py](https://github.com/o-gs/dji-firmware-tools/blob/master/comm_serialtalk.py)
- The JKU thesis (Mavic Pro 1, Wi-Fi mode) concludes: "Neither full nor partial payload encryption has been implemented." It notes the link-layer WPA2 "AES in counter mode and CBC MAC" protection, and that the DUML header bits indicate "the DUML-Body's encryption mode … None, AES 128, Self Def, XOR, DES 56, DES 112, AES 192 or AES256". It also records "The MP1, Phantom 3, Phantom 4, etc. encode con(0x55), while Phantom 1, Phantom 2, Naza M, etc. encode con(0xAB)" as the start delimiter. Consumer drone only — [Christof, "DJI Wi-Fi Protocol Reverse Engineering", JKU Linz, Nov 2021](https://epub.jku.at/obvulihs/download/pdf/6966648?originalFilename=true)
- An o-gs issue (#25, P3) documents an inter-module UART: "The physical link is UART, 115200 8N1 as usual" for FC↔battery, with a separate 0xAB-header format. I saw no encryption there. Phantom 3 only — [o-gs issue #25](https://github.com/o-gs/dji-firmware-tools/issues/25)

### Inferences
- The A3 runs 2016-era firmware alongside the Phantom 3/4 era, which dissectors show as plaintext DUML. Plaintext internal DUML on the A3 is therefore plausible but **not demonstrated**. The LB2 RF link is a separate radio layer, and no public analysis of its encryption was found. It does not matter for an onboard tap, which would sit after the radio.

### Gaps
- No source on CAN-level authentication or encryption for A3, N3 or LB2.
- I did not verify how the Open Protocol encryption flag (OSDK app key) applies to 0x02/0x03 and 0x02/0x04 pushes versus the 0x02/0x00 broadcast.

## 4. Practical feasibility of an ESP32 TWAI listen-only tap (bitrate, connector access, risk)

### Takeaway
It is technically possible to attach a listen-only CAN node to A3 CAN1 or CAN2, but it is **not worth doing for this goal**. The bitrate, IDs and DUML-over-CAN framing for the A3 are unpublished, mission traffic probably does not cross CAN1, and there is no public decoder to build on. Listen-only mode itself is low-risk for bus integrity if wired correctly. The bigger risks are the physical tap on the GPS/compass bus and wiring mistakes.

### Cited Findings
- The A3 exposes CAN1 (GPS-Compass Pro, RTK, Zenmuse gimbal, landing gear), an "Extended CAN1 Port" on the GPS-Compass Pro module ("Dedicated DJI CAN-Bus port. Communicates with DJI devices (e.g. Real Time Kinematic (RTK) GPS system)"), and CAN2 "Communicates with an SDK device" — [A3 User Manual](https://dl.djicdn.com/downloads/a3/en/A3_and_A3_Pro_User_Manual_en_160520.pdf)
- The DJI A3 support FAQ says "in the future, CAN 1 will be supported by the SDK", which implies CAN1 was not an SDK interface (search summary) — [DJI A3 support](https://www.dji.com/support/product/a3)
- A Hackaday log on DJI RoboMaster S1 CAN describes tapping through an unused connector with a logic analyzer and RS-485 transceiver. This is a different DJI product — [Hackaday.io project 167276 log](https://hackaday.io/project/167276/log/168046)
- Naza CAN data required a transmitted 1 Hz heartbeat (0x108-1007) to enable OSD emission. This kind of gating would rule out a receive-only design if the A3 behaves similarly — [STorM32 wiki](https://www.olliw.eu/storm32bgc-v2-wiki/CAN_Bus_Communication)

### Inferences
- The ESP32 TWAI controller supports a listen-only mode that sends no ACKs or error frames. The ESP-IDF documentation was not opened in this session, so this rests on prior knowledge. Paired with a transceiver held in silent/standby-RX mode (e.g. a TJA1051 with the S pin high), it puts no dominant bits on the bus. The remaining risks are a short or reversed CANH/CANL at the splice, an extra stub or termination change on a bus that carries GPS and compass data, and the ESP32 coming out of listen-only mode through a firmware bug. That last one can be prevented in hardware with the transceiver silent pin.
- The bitrate is unknown for the A3. 1 Mbit/s is common folklore for DJI CAN but was **not confirmed** by any source opened here. Auto-baud by trial in listen-only mode is possible.
- The extended CAN1 port on the GPS-Compass Pro is the least invasive physical access point, since it is a spare DJI connector. The connector type and pinout were not found.

### Gaps
- A3 CAN bitrate, frame IDs, connector part number and pinout: not found publicly.
- No evidence either way on whether the A3 emits anything useful on CAN without a heartbeat or handshake.

## 5. Legal / terms-of-service considerations (brief)

### Takeaway
DJI's developer EULA and API terms prohibit reverse engineering without DJI's written consent. A purely passive tap on your own aircraft that uses no DJI SDK code may fall outside those contracts, but sniffing DJI's internal protocol is still reverse engineering of DJI firmware behaviour. Reading the *documented* Open Protocol pushes on the API UART is the cleanest position, because DJI publishes that format for SDK devices.

### Cited Findings
- DJI's developer EULA bars users from trying to "port, reverse compile, reverse assemble, reverse engineer" without DJI's prior written consent (excerpt from a search summary; full text not opened) — [DJI Developer EULA](https://developer.dji.com/policies/eula)
- DJI API terms forbid attempts to "derive or gain access to any software component of the API through reverse engineering or decompiling" outside express authorization, and allow immediate termination for violations (search summary) — [DJI developer policy page](https://developer.dji.com/policies/flight_record)
- The DUML protocol "is widely undocumented (no official documentation). It is mostly reverse engineered knowledge" (search summary) — [Hackaday.io DJI FPV battery project](https://hackaday.io/project/188194-dji-fpv-battery-breakout-mod-2-communication)

### Inferences
- In the US, 17 U.S.C. §1201(f) contains a statutory interoperability exception to the anti-circumvention rules. It matters only if a technical protection measure is circumvented. Passively reading plaintext traffic is generally not circumvention. This rests on general knowledge; I did not open the statute in this session, and it is not legal advice. The project's jurisdiction (likely Panama) may differ.
- Contract (EULA/ToS) risk is the practical one: loss of SDK access or warranty. Criminal or civil exposure for a receive-only tap on owned hardware appears low, but this is unverified.

### Gaps
- I did not open the full current DJI EULA, the DMCA §1201(f) text or the applicable Copyright Office exemptions, nor any Panamanian law on the topic.
